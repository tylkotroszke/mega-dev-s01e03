Problems and investigation scopes

The mechanisms below are specified in the exported code and supported by reporter examples. We have not run the production parser or form. Report totals below are disjoint work-item scopes, not a claim that every report’s underlying cause has been verified. The independent body-evidence table below makes that limit visible rather than relying on a footnote.

Shared parser: the common parser reads input month first even for a tenant whose locale puts the day first. An ambiguous day/month can become a different calendar date. The scope includes app and email reports, plus booking-v2 forms; booking-v3 app/email reports still use this route. Fix locale-aware parsing or require an unambiguous input format, and verify stored dates and invite dates together.

Booking-v3 hint: the form displays MM/DD/YYYY, but reads the date in the day-first tenant’s order. A person following the hint can therefore submit a different date from the one intended. Align the hint and validation with the actual parser for that tenant. Fixing only the shared parser does not correct the form’s promise to its user.

Qualified observations: the desk notes describe temporal symptoms in some reports. The export’s readAs convention explicitly says to count those reports in their assigned group and footnote them. Preserve their wording and uncertainty; the note list alone does not establish an independent mechanism or justify an additional issue.

The classification uses the tenant directory’s locale and form version with the report’s channel, as implemented in causes.ts and locales.ts. meta.intakeTag is a browser-based guess; neither that tag nor meta.browserLocale establishes the tenant’s settings. Tenant configuration is a snapshot, so historical changes would need confirmation from the live desk. The report counts follow this specified grouping after deduplication. Report bodies and desk notes remain available for checking what the grouping does and does not establish.

The accepted decision 0001 and triage text prescribe matching normalized subjects. Their review dates are stale under the KB’s own review policy. The explorer actually compares causes using tenant and channel: identical subjects can need different fixes, and different subjects can need one fix. Changing punctuation cannot fix that mismatch between the written rule and its working example. The explorer itself has no report-body or report-ID input. It demonstrates formatting routes; it cannot establish that a temporal observation has the same cause as a parser report.

For this export, a booking-v3 form at Alder Physio differs from an app report at the same tenant; form reports at Copper Studio and Morrow Tax also differ because the form versions differ. Unknown tenants are not evidence of a shared cause and must stay unmerged pending investigation.

The support desk covers sched-prod and other products. Outside this date incident, do not reuse this classifier as a universal merge rule. Read the report, identify the product and affected workflow, obtain the configuration and reproduction evidence relevant to that product, and merge only when evidence supports the same underlying problem and fix. Preserve report IDs, counts and first-received dates. When evidence is missing, keep reports separate for triage.
